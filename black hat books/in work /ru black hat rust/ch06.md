# Глава 6. Поиск уязвимостей

## 6.1 Что такое уязвимость

Проект OWASP определяет уязвимость следующим образом: уязвимость — это дыра или слабое место в приложении, которая может быть ошибкой проектирования или ошибкой реализации и которая позволяет атакующему причинить вред заинтересованным сторонам приложения.

Что считать уязвимостью, зависит от вашей модели угроз (Что такое модель угроз? Мы узнаем больше об этом в главе 11).

Например, один баг был вознаграждён $700 за простую утечку DNS. Но в контексте программ, защищающих приватность, эта утечка довольно важна и может подвергнуть людей опасности.

В том же духе такой инструмент, как `npm audit`, может сообщить о куче уязвимостей в ваших зависимостях. В реальности, даже если ваше собственное программное обеспечение использует эти уязвимые зависимости, оно может быть вовсе не уязвимо, так как уязвимые функции могут не вызываться или вызываться так, что уязвимость невозможно задействовать.

## 6.2 Слабость и уязвимость (CWE и CVE)

CVE — это список записей, каждая из которых содержит идентификационный номер, описание и как минимум одну публичную ссылку — об известных публично уязвимостях и проблемах кибербезопасности.

Вы можете найти список существующих CVE на сайте https://www.cvedetails.com (который мы скрейпили в предыдущей главе).

CWE (Common Weakness Enumeration — общее перечисление слабостей) — это создаваемый сообществом список типов слабостей программного и аппаратного обеспечения.

Вы можете найти список CWE в сети: https://cwe.mitre.org.

Таким образом, слабость (CWE) — это шаблон, который может привести к уязвимости (CVE).

Не все уязвимости имеют связанный CVE ID. Иногда потому, что нашедший уязвимость человек считает, что оно того не стоит, иногда потому, что они не хотят публичного раскрытия уязвимости.

## 6.3 Уязвимость и эксплойт

В то время как уязвимость — это дыра в приложении, эксплойт — это фрагмент кода, который использует эту уязвимость в наступательных целях.

Написание эксплойта известно как вепонизация (weaponization): процесс превращения программной ошибки в готовое к применению цифровое оружие.

Написание эксплойтов — это тонкое искусство, требующее глубокого знания технологии, в которой была найдена уязвимость.

Например, написание эксплойта для XSS-уязвимости (как мы увидим ниже) требует глубокого знания веба и экосистемы JavaScript, чтобы обойти ограничения, накладываемые уязвимостью, межсетевыми экранами веб-приложений (WAF) и браузерами, например ограниченное количество символов.

## 6.4 0 Day и CVE

Не все уязвимости публичны. Некоторые обнаруживают и держат в тайне, чтобы вепонизировать их или продать людям, которые их вепонизируют.

Непубличный, но известный некоторым эксплойт называется 0 Day (нулевой день).

Подробнее на эту тему можно прочитать в превосходной статье Wikipedia о рынке эксплойтов нулевого дня. (https://en.wikipedia.org/wiki/Market_for_zero-day_exploits)

С другой стороны, CVE — это известная уязвимость, затрагивающая продукт, даже если для этой уязвимости не существует публичного эксплойта.

## 6.5 Веб-уязвимости

Я не думаю, что игрушечные примеры уязвимостей чему-то учат.

Вот почему, вместо того чтобы создавать игрушечные примеры уязвимостей исключительно ради этой книги — уязвимостей, которые вы никогда не встретите в реальных ситуациях, — я составил подборку того, что, по моему мнению, относится к лучшим разборам по поиску и эксплуатации уязвимостей, затрагивающих реальные продукты и компании.

## 6.6 Инъекции

Инъекции — это семейство уязвимостей, в которых в приложение можно внедрить вредоносную нагрузку для достижения различных эффектов.

Корень всех инъекций — неправильная обработка входных данных программ.

Что является примерами входных данных программы?

- Для веб-приложения — это поля ввода формы или загруженный файл.
- Для VPN-сервера — это сетевые пакеты.
- Для wifi-клиента — это, среди прочего, имена обнаруженных wifi-сетей.
- Для почтового приложения — это письма, их метаданные и вложения.
- Для чат-приложения — это сообщения, имена пользователей и медиа.
- Для видеоплеера — это видеофайлы и файлы субтитров.
- Для музыкального плеера — аудиофайлы и их метаданные.
- Для терминала — это ввод пользователя и вывод приложений командной строки.

## 6.7 HTML-инъекции

HTML-инъекция — это уязвимость, при которой атакующий может внедрить произвольный HTML-код в ответы приложения, отображающего HTML-код.

**Рисунок 6.1: HTML-инъекция**

![Рисунок 6.1](figures/figure-6.1.png)


Она может использоваться для дефейса или обмана пользователей, заставляя их совершать вредные (для них) действия, например подменяя форму входа на вредоносную.

Вот пример псевдокода, уязвимого к HTML-инъекциям:

```javascript
function comment(req, res) {
  let new_comment = req.body.comment;


    // comment is NOT sanitized when saved to database
    save_to_db(new_comment);


    let all_comments = db.find_comments();


    let html = "";


    // comments are NOT sanitized when rendered
    for comment in comments {
        html += "<div><p>" + comment + "</p></div>";
    }


    res.html(html);
}
```

## 6.8 SQL-инъекции

В 2010-е годы SQL-инъекции были в моде благодаря славе PHP и его небезопасным API. Теперь они встречаются всё реже и реже благодаря ORM и другим веб-фреймворкам, которые обеспечивают хорошую безопасность по умолчанию.

**Рисунок 6.2: SQL-инъекция**

![Рисунок 6.2](figures/figure-6.2.png)


Вот пример псевдокода, уязвимого к SQL-инъекции:

```javascript
function get_comment(req, res) {
    let comment_id = req.query.id;


    // concataining strings to build SQL queries is FATAL
    let sql_query = "SELECT * FROM comments WHERE id = " + comment_id;


    let comment = db.execute_query(sql_query);


    let html = template.render(comment);


    res.html(html);
}
```

Который можно эксплуатировать следующим запросом:

```text
GET https://kerkour.com/comments?id=1 UNION SELECT * FROM users
```

### 6.8.1 Слепая SQL-инъекция

Предпосылка для уязвимости SQL-инъекции — если сайт выводит результат SQL-запроса на веб-страницу. Иногда это не так, но уязвимость всё же есть под капотом.

Этот сценарий называется слепой инъекцией, потому что мы не видим результат инъекции.

Вы можете научиться эксплуатировать их здесь: https://portswigger.net/web-security/sql-injection/blind

### 6.8.3 Инъекции в другие языки запросов баз данных

После повального увлечения PHP и Ruby пришёл Node.JS.

Всё стало JSON-объектами. Даже записи баз данных, и именно так взлетел mongoDB. Приложения на реляционных базах данных могут быть уязвимы к SQL-инъекциям. Приложения на mongoDB могут быть уязвимы к инъекциям в язык запросов mongoDB.

Как и в случае с другими видами инъекций в базы данных, идея в том, чтобы найти уязвимый вход, который не санитизируется и передаётся в базу данных как есть.

## 6.9 XSS

XSS (Cross Site Scripting — межсайтовый скриптинг) инъекции — это вид атаки, при которой вредоносный скрипт (в большинстве случаев JavaScript, так как он понимается всеми веб-браузерами) внедряется в веб-сайт.

**Рисунок 6.3: XSS**

![Рисунок 6.3](figures/figure-6.3.png)


Если количество SQL-инъекций в дикой природе со временем сократилось, то количество XSS, с другой стороны, взорвалось за последние годы, когда значительная часть логики веб-приложений живёт на стороне клиента (особенно с одностраничными приложениями (SPA)).

Например, у нас есть следующий HTTP-запрос:

```text
POST /myform?lang=fr
Host: kerkour.com
User-Agent: curl/7.64.1
Accept: */*
Content-Type: application/json
Content-Length: 35


{"username":"xyz","password":"xyz"}
```

Сколько потенциальных точек инъекции вы можете найти?

Я вижу как минимум 4:

- В URL: параметр запроса `lang`
- Заголовок `User-Agent`
- Поле `username`
- Поле `password`

Всё это предоставленный пользователем ввод, который может обрабатываться (а может и не обрабатываться) веб-приложением, и если его добросовестно не проверять, это приведёт к XSS-инъекции.

Вот пример псевдокода, уязвимого к XSS-инъекции:

```javascript
function post_comment(req, res) {
    let comment = req.body.comment;


    // You need to sanitize inputs!
    db.create_comment(comment);


    res(comment);
}
```

Существует 3 вида XSS:

- Отражённый XSS
- Сохранённый XSS
- DOM-based XSS

### 6.9.1 Отражённый XSS

Отражённый XSS — это инъекция, которая существует только в течение времени жизни запроса.

В основном они встречаются в параметрах запроса и HTTP-заголовках.

Например:

```text
GET /search?q=<script>alert(1)</script>
Host: kerkour.com
User-Agent: <script>alert(1)</script>
Accept: */*
```

Проблема отражённого XSS для атакующих в том, что их сложнее вепонизировать: нагрузку нужно предоставить в запросе, в большинстве случаев в URL. Это может вызвать подозрения!

Один из трюков, позволяющих скрыть XSS-нагрузку в URL, — использование сокращателя ссылок. Например, следующий URL:

```text
https://kerkour.com/search?q=<script>alert(1)</script>
```

Может быть скрыт так:

```text
https://minifiedurl.co/q9n7l
```

Таким образом, жертвы могут быть гораздо менее подозрительными, так как мы все привыкли кликать по сокращённым URL, например в описаниях видео на YouTube.

### 6.9.2 Сохранённый XSS

Сохранённый XSS — это инъекция, которая существует дольше, чем время жизни запроса. Она сохраняется сервером веб-приложения и передаётся в будущих запросах.

Например, комментарий в блоге.

В основном они встречаются в данных форм и HTTP-заголовках.

Например:

```text
POST /myform
Host: kerkour.com
User-Agent: <script>alert(1)</script>
Accept: */*
Content-Type: application/json
Content-Length: 35


{"comment":"<script>alert(1)</script>"}
```

После сохранения сервером нагрузка будет передана потенциально многим жертвам.

Один из видов сохранённого XSS, который разработчики часто упускают из виду, — внутри SVG-файлов. Да, SVG-файлы могут выполнять блоки `<script>`.

Вот пример такого вредоносного файла:

```xml
<?xml version="1.0" standalone="no"?>
<!DOCTYPE svg PUBLIC "-//W3C//DTD SVG 1.1//EN" "http://www.w3.org/Graphics/SVG/1.1/DTD/svg11.dtd">
<svg version="1.1" baseProfile="full" xmlns="http://www.w3.org/2000/svg">
  <polygon id="triangle" points="0,0 0,50 50,0" fill="#009900" stroke="#004400"/>
  <script type="text/javascript">
     alert(document.domain);
  </script>
</svg>
```

Вы можете увидеть это в действии в сети: https://kerkour.com/imgs/xss.svg, где вас встретит славное JavaScript-предупреждение. А теперь подумайте обо всех тех формах загрузки изображений, которые любезно принимают это изображение и передают его всем пользователям веб-приложения.

### 6.9.3 DOM-based XSS

DOM-based XSS — это XSS-инъекция, в которой нагрузка не возвращается сервером, а вместо этого выполняется напрямую браузером путём модификации DOM.

В большинстве случаев входная точка DOM-based XSS — это URL, например:

```html
<script>
document.write('...' + window.location + '...');
</script>
```

Отправив нагрузку в `window.location` (URL), атакующий сможет выполнить JavaScript в контексте жертвы, даже без участия сервера в этом сценарии. В случае одностраничного приложения нагрузка может поразить жертву даже без обращения к серверу, что делает расследование невозможным без инструментирования на стороне клиента.

### 6.9.4 Почему это плохо

Воздействие XSS-уязвимости — выполнение скрипта в контексте жертвы. Сегодня это означает, что у атакующих в большинстве случаев полный контроль: они могут красть токены сессии, выполнять произвольные команды, похищать личности, дефейсить веб-сайты и так далее…

Отметим, что в некоторых обстоятельствах XSS-инъекции могут быть превращены в удалённое выполнение кода (RCE, подробнее ниже) благодаря серверному рендерингу (SSR) и безголовым браузерам.

## 6.10 Server Side Request Forgery (SSRF)

Server Side Request Forgery (подделка запросов на стороне сервера) происходит, когда атакующий может отправлять HTTP-запросы с сервера веб-приложения. В большинстве случаев атакующий также может прочитать ответ на запрос.

Вот пример псевдокода, уязвимого к SSRF:

**Рисунок 6.4: SSRF**

![Рисунок 6.4](figures/figure-6.4.png)


```javascript
function check_url(req, res) {
    let url = req.body.url;


    // You need to check the url against an allowlist
    let response = http_client.get(url);


    // DON'T display the result of the HTTP request
    res(response);
}
```

Этот вид уязвимости особенно разрушителен в облачных средах, где могут быть получены некоторые метаданные и/или учётные данные: https://gist.github.com/jhaddix/78cece26c91c6263653f31ba453e273b.

### 6.10.1 Почему это плохо

В большинстве случаев воздействие SSRF — это доступ к внутренним сервисам, которые не предназначались для публичного доступа и потому могут не требовать аутентификации (внутренние дашборды, базы данных…). Я думаю, мне не нужно писать роман, чтобы вы поняли, насколько это может быть вредно.

### 6.10.2 Примеры из практики

- [Full Read SSRF on Gitlab's Internal Grafana](https://hackerone.com/reports/878779)
- [Server Side Request Forgery (SSRF) at app.hellosign.com leads to AWS private keys disclosure](https://hackerone.com/reports/1011979)
- [SSRF chained to hit internal host leading to another SSRF which allows reading internal images](https://hackerone.com/reports/894952)

## 6.11 Cross-Site Request Forgery (CSRF)

 CSRF - Cross-Site Request Forgery (подделка межсайтовых запросов) — это уязвимость, которая позволяет атакующему заставить пользователя выполнить нежелательные действия.

**Рисунок 6.5: CSRF**

![Рисунок 6.5](figures/figure-6.5.png)


Существует два семейства CSRF:

Первое — с использованием форм. Представьте сценарий, в котором приложение позволяет администраторам обновлять роли других пользователей. Что-то вроде:

```php
$current_user = $_COOKIE["id"];
$role = $_POST["role"];
$username = $_POST["username"];


if (is_admin($current_user)) {
    set_role($role, $username);
}
```

Если я размещу на своём сайте malicious.com форму, подобную этой:

```html
<html>
    <body>
      <form action="https://kerkour.com/admin" method="POST">
         <input type="hidden" name="role" value="admin" />
         <input type="hidden" name="username" value="skerkour" />
    </form>
    <script>
      document.forms[0].submit();
    </script>
  </body>
</html>
```

Любой администратор `kerkour.com`, который посетит `malicious.com`, отправит (даже не подозревая об этом) запрос к kerkour.com, сообщающий этому сайту назначить меня администратором.

Второе — с использованием URL. Уязвимость кроется в том факте, что GET-запросы могут выполнять действия вместо доступных запросов только для чтения.

```text
GET https://kerkour.com/admin?set_role=admin&user=skerkour
```

Представьте, что я отправлю этот URL администратору уязвимого сайта, и теперь я сам администратор :)

Так как CSRF опирается на cookie, одностраничные приложения в большинстве случаев невосприимчивы к этим уязвимостям.

### 6.11.1 Почему это плохо

Как и XSS, CSRF-уязвимости позволяют атакующим выполнять команды с правами другого пользователя. Если жертва — администратор, у них есть привилегии администратора, и, таким образом, они могут скомпрометировать всё приложение.

### 6.11.2 Примеры из практики

- [TikTok Careers Portal Account Takeover](https://hackerone.com/reports/1019290)
- [Account takeover just through csrf](https://hackerone.com/reports/165373)

## 6.12 Открытое перенаправление

Открытое перенаправление (open redirect) — это вид уязвимости, позволяющий атакующему перенаправить пользователя легитимного сайта на другой сайт.

Вот пример псевдокода, уязвимого к открытому перенаправлению:

```javascript
function do_something(req, res) {
  let redirect_url = req.body.redirect;


  // You need to check redirect targets againt an allowlist
  res.redirect(redirect_url);
}
```

**Рисунок 6.6: Открытое перенаправление**

![Рисунок 6.6](figures/figure-6.6.png)


Например, жертва может посетить https://kerkour.com/login?redirect=malicious.com и быть перенаправлена на malicious.com.

Как и XSS с CSRF, их можно скрыть с помощью сокращателей ссылок.

### 6.12.1 Почему это плохо

Наиболее очевидное применение этого вида уязвимости — фишинг, так как жертва может думать, что кликнула по легитимной ссылке, но в итоге попасть на злую.

## 6.13 Перехват (суб)домена

(Суб)домен тайкоуверы (subdomain takeover) — определённо те самые легкодоступные плоды (low-hanging fruits), которые проще всего найти, если вы хотите быстро заработать несколько сотен долларов на багбаунти-программах.

Уязвимость возникает из-за того, что DNS-запись указывает на публичный облачный ресурс, который больше не находится под контролем компании, владеющей доменом.

Допустим, у вас есть веб-приложение на Heroku (облачный провайдер).

**Рисунок 6.7: Перехват (суб)домена**

![Рисунок 6.7](figures/figure-6.7.png)


Чтобы указать собственным доменом на приложение, вам нужно будет настроить что-то вроде CNAME-записи DNS, указывающей на myapp.herokuapp.com.

Время летит, и вы полностью забываете, что эта DNS-запись существует, и решаете удалить своё приложение Heroku. Теперь имя myapp.herokuapp.com снова доступно любому, кто захочет создать приложение с таким именем.

Итак, если злоумышленник создаст приложение Heroku с именем `myapp`, он сможет обслуживать контент с вашего собственного домена, так как тот всё ещё указывает на myapp.herokuapp.com.

Мы взяли пример приложения Heroku, но есть множество сценариев, в которых такая ситуация может произойти:

- Плавающий IP-адрес от публичного облачного провайдера, такого как AWS
- Блог почти на любой SaaS-платформе для блогов
- CDN
- S3-корзина (bucket)

### 6.13.1 Почему это плохо

Во-первых, так как субдомены могут иметь доступ к cookie других субдоменов (таких как www…), контроль над субдоменом может позволить атакующим выкрасть эти cookie.

Во-вторых, перехват субдомена может также позволить атакующим создавать фишинговые страницы с легитимными URL.

Наконец, перехват субдомена может позволить атакующим распространять вводящую в заблуждение информацию. Например, если люди, выступающие против компании, захватят субдомен press.company.com, они могут распространять ложные сообщения, в то время как весь остальной мир будет думать, что эти сообщения исходят от PR-отдела взломанной компании.

- [Subdomain Takeover to Authentication bypass](https://hackerone.com/reports/335330)
- [Subdomain Takeover Via Insecure CloudFront Distribution cdn.grab.com](https://hackerone.com/reports/352659)
- [Subdomain takeover of v.zego.com](https://hackerone.com/reports/240561)

## 6.14 Произвольное чтение файлов

Уязвимости произвольного чтения файлов (arbitrary file read) позволяют атакующим читать содержимое файлов, которые должны были остаться приватными.

**Рисунок 6.8: Произвольное чтение файлов**

![Рисунок 6.8](figures/figure-6.8.png)


Вот пример псевдокода, уязвимого к произвольному чтению файлов:

```javascript
function get_asset(req, res) {
    let asset_id = req.query.id;


    let asset_content = file.read('/assets/' + asset_id);


    res(asset_content);
}
```

Её можно эксплуатировать так:

```text
https://example.com/assets?id=../etc/passwd
```

Видите трюк? Вместо легитимного `id` мы отправляем путь к чувствительному файлу.

Так как в Unix-подобных системах всё является файлом, секретная информация, такая как учётные данные баз данных, ключи шифрования или SSH-ключи, могут находиться где-то в файловой системе. Любой атакующий, способный прочитать эти файлы, быстро сможет нанести серьёзный ущерб уязвимому приложению.

Вот некоторые примеры файлов, содержимое которых может быть интересно:

```text
/etc/passwd
/etc/shadow
/proc/self/environ
/etc/hosts
/etc/resolv.conf
/proc/cpuinfo
/proc/filesystems
/proc/interrupts
/proc/ioports
/proc/meminfo
/proc/modules
/proc/mounts
/proc/stat
/proc/swaps
/proc/version
~/.bash_history
~/.bashrc
~/.ssh/authorized_keys
~/.ssh/id_dsa
.env
```

### 6.14.1 Почему это плохо

Как только атакующий может читать содержимое любого файла в файловой системе, это всего лишь вопрос времени, прежде чем он сможет повысить уязвимость до более серьёзной и завладеть сервером.

Вот пример повышения уязвимости чтения файлов до удалённого выполнения кода: [Read files on the application server leads to RCE](https://hackerone.com/reports/869345)

## 6.15 Отказ в обслуживании (DoS)

Цель атаки типа «отказ в обслуживании» (Denial of Service, DoS) — сделать сервис недоступным для его легитимных пользователей.

**Рисунок 6.9: Отказ в обслуживании**

![Рисунок 6.9](figures/figure-6.9.png)


Мотивация такой атаки в большинстве случаев финансовая: будь то требование выкупа за прекращение DoS или отрезание конкурента в период, когда ожидается большое количество продаж.

Как вы могли догадаться, блокирование цикла событий Rust часто приводит к DoS, когда крошечное количество запросов может заблокировать всю систему.

Есть также двоюродный брат DoS: DDoS — распределённый отказ в обслуживании (Distributed Denial of Service), где конечная цель та же (сделать сервис недоступным для легитимных пользователей), но метод другой. DDoS обычно выполняются не одним атакующим, а ботнетом, контролируемым атакующим.

### 6.15.1 Почему это плохо

Смогут ли ваши клиенты купить футболки на вашем сайте, если они не могут получить к нему доступ?

Уязвимости произвольной записи файлов (arbitrary file write) позволяют атакующим перезаписывать содержимое файлов, которые должны были остаться нетронутыми.

**Рисунок 6.11: Произвольная запись файлов**

![Рисунок 6.11](figures/figure-6.11.png)


Вот пример псевдокода, уязвимого к произвольной записи файлов:

```javascript
function upload_file(req, res) {
    let file = req.body.file;
    let file_name = req.body.file_name;
```

```text

```

Когда уязвимый код обработает загрузку, он перезапишет файл `.ssh/authorized_keys` пользователя root, отдав атакующему ключи от королевства.

## 6.17 Уязвимости памяти

Эти уязвимости — одна из причин популярности Rust, благодаря которому вы невосприимчивы к ним, пока держитесь подальше от `unsafe`. Это то, что мы называем «безопасность памяти» (memory safety).

В основном они поражают низкоуровневые языки программирования, такие как C и C++, где вам приходится вручную управлять памятью, но, как мы увидим, динамические языки, такие как Ruby и Python, которые опираются на множество пакетов, написанных на самом C или C++, также могут быть (косвенно) уязвимы.

## 6.18 Переполнение буфера

Вот пример псевдокода, уязвимого к переполнению буфера:

```c
function copy_string(input []char) []char {
    // buffer is too small if len(input) > 32 which will lead to a buffer overflow
    let copy = [32]char;


    for (i, c) in input {
        copy[i] = c;
    }


    return copy;
}
```

Как Rust предотвращает этот вид уязвимости? У него есть проверки границ буферов, и он запаникует, если вы попытаетесь заполнить буфер большим количеством данных, чем его размер.

## 6.19 Использование после освобождения (use after free)

Баг использования после освобождения (use after free), как указывает название, — это когда программа повторно использует память, которая уже была освобождена.

Так как память считается свободной для аллокатора памяти, последний мог переиспользовать её для хранения других данных.

Вот пример псевдокода, уязвимого к использованию после освобождения:

```c
function allocate_foobar() []char {
    let foobar = malloc([]char, 1000);
}


function use_foobar(foobar []char) {
    // do things
    free(foobar);
}


function also_use_foobar(foobar []char) {
    // do things
}



function main() {
    let foobar = allocate_foobar();


    use_foobar(foobar);


    // do something else
    // ...


    // !! we reuse foobar after freeing it in use_foobar
    also_use_foobar(foobar);
}
```

### 6.19.1 Почему это плохо

Аллокатор памяти может переиспользовать ранее освобождённую память для других целей. Это означает, что уязвимость использования после освобождения может привести не только к повреждению данных, но и к удалённому выполнению кода, если будет перезаписан важный указатель.

С точки зрения атакующего, уязвимости использования после освобождения не так надёжны из-за природы аллокаторов памяти, которые не детерминированы.

### 6.19.2 Примеры из практики

- [Exploiting a textbook use-after-free in Chrome](https://starlabs.sg/blog/2021/07/exploiting-a-textbook-use-after-free-in-chrome/)

## 6.20 Двойное освобождение (double free)

Название этого бага само за себя говорит: двойное освобождение — это когда переменная, выделенная в куче (например, с помощью malloc), освобождается дважды.

Это испортит состояние аллокатора памяти и приведёт к неопределённому поведению.

Вот пример псевдокода, уязвимого к двойному освобождению:

```c
function allocate_foobar() []char {
  let foobar = malloc([]char, 1000);
}


function use_foobar(foobar []char) {
    // do things
    free(foobar);
}


function main() {
    let foobar = allocate_foobar();


    use_foobar(foobar);


    // !! foobar was already freed in use_foobar
    free(foobar);
}
```

### 6.20.1 Почему это плохо

Двойное освобождение указателя испортит состояние аллокатора памяти.

Как и уязвимости использования после освобождения, уязвимости двойного освобождения приводят к неопределённому поведению. В большинстве случаев это означает крах или повреждение данных. Иногда это можно эксплуатировать для выполнения кода, но на практике этого действительно трудно достичь.

## 6.23 Переполнение целых чисел (и потеря значимости)

Уязвимость переполнения целых чисел возникает, когда арифметическая операция пытается создать числовое значение вне диапазона, который может хранить числовая переменная.

Например, переменная `uint8` (u8 в Rust) может хранить значения от 0 до 255, потому что она кодируется 8 битами. В зависимости от языка это часто приводит к неопределённому поведению.

Вот пример псевдокода, уязвимого к переполнению целых чисел:

```c
function withdraw(user id, amount int32) {
    let balance: int32 = find_balance(user);


    if (balance - amount > 0) {
        return ok();
    } else {
        return error();
    }
}
```

Так как `balance` и `amount` кодируются в `int32`, они переполнятся после 2,147,483,647 и -2,147,483,648. Если мы попытаемся вычесть 4,294,967,295 (примерно) из 10,000 (balance), в C результат будет 10001… который положителен и может погубить ваш банковский бизнес.

Вот ещё один, более тонкий пример:

```c
// n is controlled by attacker
function do_something(n uint32) {
    let buffer = malloc(sizeof(*char) * n);


    for (i = 0; i < n; i++)
        buffer[i] = do_something();
    }
}
```

Если мы зададим `n` как слишком большое число, которое переполняет `uint32` при умножении на размер указателя (4 байта в 32-битной системе), например 1073741824, происходит переполнение целых чисел, и мы выделяем буфер размером 0, который будет переполнен последующим циклом for.

Интересно отметить, что в режиме отладки (`cargo build` или `cargo run`) Rust запаникует при встрече с переполнением целых чисел, но в release-режиме (`cargo build --release` или `cargo run --release`) Rust не запаникует. Вместо этого выполняется обёртывание по дополнению до двойки: программа не упадёт, но переменная будет содержать недопустимое значение.

```rust
let x: u8 = 255;


// x + 1 = 0 (and not 256)
// x + 2 = 1 (and not 257)
// x + 3 = 2 (and not 258)
```

Подробнее об этом поведении можно прочитать в книге о Rust.

### 6.23.1 Почему это плохо

Этот вид уязвимости стал популярным со смарт-контрактами, где из-за бракованных контрактов были украдены большие суммы денег.

Уязвимости переполнения целых чисел можно использовать для управления потоком выполнения программы или для запуска других уязвимостей (таких как переполнение буфера из примера выше).

## 6.24 Логическая ошибка

Логическая ошибка — это любая ошибка, позволяющая атакующему манипулировать бизнес-логикой приложения. Например, атакующий может заказать множество товаров в интернет-магазине по цене 0, или атакующий может получить чувствительные данные, которые обычно разрешено получать только администраторам.

## 6.25 Гонки данных (race condition)

Гонка данных возникает, когда программа полагается на множество конкурентных операций и на последовательность или сроки выполнения этих операций для получения корректного вывода.

Из этого следует, что если по какой-то причине, например из-за отсутствия синхронизации, последовательность или сроки выполнения операций изменяются, возникает ошибка.

Например, попытка прочитать значение сразу после его обновления в базе данных с конечной согласованностью (eventually-consistent).

### 6.25.1 Почему это плохо

В большинстве случаев эксплуатируемая гонка данных возникает, когда проверка выполняется конкурентно с операцией обновления (или создания, или удаления).

От произвольной записи файлов до XSS (с SVG-файлами) формы загрузки файлов также отличное место для поиска множества уязвимостей.

### 6.27.3 Поля ввода

Как мы видели, инъекции исходят из неочищенных полей ввода. Ключ к эксплуатации неочищенных полей ввода — понять, как и где они выводятся. Иногда это неочевидно, так как они могут обрабатываться каким-то алгоритмом. Например, для превращения URL в ссылки.

Также иногда поля ввода скрыты от интерфейса:

```html
<input type="hidden" id="id" name="id" value="123">
```

### 6.27.4 HTTP-заголовки

Часто упускаемый из виду вектор атаки — это HTTP-заголовки запроса.

Действительно, HTTP-заголовки иногда используются приложениями и отправляются обратно в ответе. Например, подумайте об аналитическом сервисе, который отображает топ-10 User-agent заголовков.

### 6.27.5 Опасные / устаревшие алгоритмы

Некоторые опасные и устаревшие алгоритмы, такие как `md5`, всё ещё используются в дикой природе. Если вы аудитируете приложение с доступом к исходному коду, достаточно простого `rg -i md5` (используя ripgrep).

### 6.27.6 Методы с опасными параметрами

Существует два вида методов с опасными параметрами:

- Криптографические функции, где плохая инициализация или повторное использование ключей могут привести к серьёзным ошибкам, таким как AES-GCM-256 с повторно используемыми nonce.
- Функции манипулирования данными в небезопасных по памяти языках, такие как `memset` или `strcpy` в C.

### 6.27.7 Системы аутентификации

В сердце почти каждого приложения находятся две жизненно важные системы:

Система аутентификации для проверки того, что пользователи — те, за кого себя выдают.

И система авторизации для проверки того, что пользователи имеют законные права выполнять операции, которые они хотят выполнить.

Системы аутентификации и авторизации часто сложны и разбросаны по всему приложению.

При аудите приложения поймите, какие операции требуют повышенных привилегий, и попробуйте выполнить их без этих привилегий.

### 6.27.8 Многопользовательские игры

Разработчики игр — не инженеры по безопасности. Они могут сосредотачивать своё внимание на геймплее, производительности и многих других вещах в своей области экспертизы, но не обязательно на безопасности.

Более того, сетевые стеки некоторых игр написаны на небезопасных по памяти языках, таких как C или C++. Это идеальный рецепт катастрофы (уязвимости, связанные с памятью).

Как замечание в сторону, именно поэтому вам, возможно, не стоит играть в многопользовательские игры на рабочем компьютере.

### 6.27.9 Разбор сложных форматов

Разбор сложных форматов, таких как YAML, сложен. Именно поэтому в библиотеках разбора находят множество багов. Иногда эти баги — реальные уязвимости.

В большинстве случаев это связанные с памятью уязвимости: либо из-за сложности формата, либо потому, что разработчики часто пытаются быть умными при реализации парсеров, чтобы занять первое место в микробенчмарках, и используют некоторые трюки, которые вносят баги и уязвимости.

### 6.27.10 JIT-компиляция

JIT-компиляторам (Just-In-Time) необходимо ослаблять меры безопасности современных операционных систем (по дизайну), например делать часть памяти доступной для записи и выполнения одновременно (Writable And Executable). Это означает, что связанные с памятью уязвимости эксплуатировать гораздо проще.

### 6.28.4 Сканер

Остерегайтесь: сканер, в зависимости от включённых модулей, может быть шумным и раскрывать ваши намерения. Из-за своей брутфорсоподобной природы их легко обнаружить межсетевым экранам. Так что, если вы предпочитаете оставаться в тени, будьте осторожны с тем, какие опции включаете в своём сканере.

Перехватывающий прокси поможет вам просматривать и изменять запросы на лету, приходят ли эти запросы с вашего основного компьютера или с других устройств, таких как телефон, у которого нет инструментов разработчика в браузере.

Это крайне полезно для обхода клиентской логики проверки и отправки ваших нагрузок напрямую в бэкенд инспектируемых приложений. Они также часто предлагают какую-то автоматизацию, что отлично. Это сэкономит вам массу времени!

Я считаю, что нет лучшего наступательного прокси, чем Burp Suite. У него есть бесплатная («community») версия, чтобы попробовать, и если она вам нравится и вы серьёзно относитесь к охоте за багами, вы можете купить лицензию, чтобы открыть все функции.

Burp Suite также предоставляет множество функций для автоматизации ваших запросов и атак.

Если это ваш самый первый шаг во взломе веб-приложений, вам не обязательно нужен перехватывающий прокси. Инструментов разработчика вашего веб-браузера может быть достаточно. При этом всё же отлично научиться пользоваться одним из них, так как вы быстро упрётесь в пределы, когда захотите перехватывать и изменять запросы.

## 6.29 Автоматизированный аудит

### 6.29.1 Фаззинг

Фаззинг — это метод, используемый для поиска ошибок и уязвимостей в программных проектах путём автоматической подачи в них случайных данных.

Вместо тестирования небольшого набора тестовых случаев, написанных вручную разработчиками, фаззер попробует множество входных данных и посмотрит, что произойдёт.

Фаззинг — это вид тестирования, который полностью автоматизирован и потому требует гораздо меньше человеческих усилий, чем ревью кодовой базы, особенно если кодовая база очень большая. Кроме того, фаззинг можно применять к программах с закрытым исходным кодом, в то время как реверс-инжиниринг медленный, утомительный и дорогой в человеческих часах.

#### 6.29.1.1 Установка инструментов

Рекомендуемый инструмент для начала фаззинга проекта на Rust (или, вообще-то, любой библиотеки, которую можно встроить в Rust) — использовать cargo-fuzz.

```text
$ cargo install -f cargo-fuzz
$ rustup install nightly
```

Примечание: cargo-fuzz полагается на libFuzzer. libFuzzer требует поддержку санитайзеров LLVM, поэтому пока это работает только в x86-64 Linux и x86-64 macOS. Также требуется nightly-инструментарий Rust, так как используются некоторые нестабильные флаги командной строки. Наконец, вам также понадобится C++-компилятор с поддержкой C++11.

#### 6.29.1.2 Начало работы

Во-первых, нам нужен фрагмент кода для фаззинга. Мы будем использовать идиоматически ошибочную функцию, подобную memcpy.

Предупреждение: это абсолютно не идиоматичный код на Rust, и этого стиля кода следует избегать любой ценой.

**ch_06/fuzzing/src/lib.rs**

```rust
pub fn vulnerable_memcopy(dest: &mut [u8], src: &[u8], n: usize) {
    let mut i = 0;


    while i < n {
         dest[i] = src[i];
         i += 1;
    }
}
```

Затем нам нужно инициализировать cargo-fuzz:

```text
$ cargo fuzz init
$ cargo fuzz list
fuzz_target_1
```

Он создал папку fuzz, которая сама содержит файл Cargo.toml:

Нам просто нужно добавить arbitrary в список зависимостей.

**ch_06/fuzzing/fuzz/Cargo.toml**

```toml
[package]
name = "fuzzing-fuzz"
version = "0.0.0"
authors = ["Automatically generated"]
publish = false
edition = "2018"


[package.metadata]
cargo-fuzz = true


[dependencies]
libfuzzer-sys = "0.4"
arbitrary = { version = "1", features = ["derive"] }


[dependencies.fuzzing]
path = ".."


# Prevent this from interfering with workspaces
[workspace]
members = ["."]


[[bin]]
name = "fuzz_target_1"
path = "fuzz_targets/fuzz_target_1.rs"
test = false
doc = false
```

`arbitrary` позволяет нам вывести трейт `Arbitrary`, что позволяет использовать любую структуру для фаззинга, а не просто буфер `[u8]`.

Затем мы можем реализовать нашу первую цель фаззинга:

**ch_06/fuzzing/fuzz/fuzz_targets/fuzz_target_1.rs**

```rust
#![no_main]
use libfuzzer_sys::fuzz_target;


#[derive(Clone, Debug, arbitrary::Arbitrary)]
struct MemcopyInput {
    dest: Vec<u8>,
    src: Vec<u8>,
    n: usize,
}


fuzz_target!(|data: MemcopyInput| {
      let mut data = data.clone();
      fuzzing::vulnerable_memcopy(&mut data.dest, &data.src, data.n);
});
```

И, наконец, мы можем запустить движок фаззинга:

```text
$ cargo +nightly fuzz run fuzz_target_1
```

## 6.30 Краткое содержание

- Чтобы стать хорошим охотником за уязвимостями, нужны годы, будь то уязвимости памяти или веба. Выберите одну область и хакерьте, хакерьте, хакерьте, чтобы прокачать свои навыки. Вы не можете стать хорошим в обоих за несколько недель.
- Всегда проверяйте ввод, поступающий от пользователей. Почти все уязвимости проистекают из недостаточной проверки ввода. Да, это утомительно, но вам придётся выбирать между этим и объявлением своему начальнику/клиентам, что их данные были взломаны.
- Всегда проверяйте ненадёжный ввод.
- Всегда проверяйте ненадёжный ввод еще раз.
