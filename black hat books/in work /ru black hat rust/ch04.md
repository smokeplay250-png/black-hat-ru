# Глава 4. Добавляем модули с помощью объектно-трейтовых объектов (trait objects)

Представьте, что вы хотите добавить камеру к компьютеру, у которого её нет. Вы покупаете веб-камеру и подключаете её через порт USB. А теперь представьте, что вы хотите добавить хранилище к тому же компьютеру. Вы покупаете внешний жёсткий диск и также подключаете его через аналогичный порт USB.

В этом сила дженериков, применённых к миру физических гаджетов. Порт USB — это универсальный порт, а аксессуар, который к нему подключается, — это модуль. У вас нет портов под конкретные устройства: специального порта для веб-камер конкретного вендора, другого порта для другого вендора, ещё одного для вендора USB-дисков и так далее… Вы можете подключить почти любое USB-устройство к любому USB-порту, и оно заработает (если совместимо с драйверами…). Ваш производитель ПК не обязан планировать любой модуль, который вы можете захотеть подключить к вашему компьютеру. Ему достаточно следовать универсальной и общей спецификации USB.

То же самое относится и к коду. Функция может выполнять конкретную задачу для конкретного типа, а обобщённая (generic) функция может выполнять конкретную задачу для некоторых (подробнее позже) типов.

`add` может складывать только две переменные `i64`.

```rust
fn add(x: i64, y: i64) -> i64 {
    return x + y;
}
```

Здесь `add` может складывать две переменные любого типа.

```rust
fn add<T>(x: T, y: T) -> T {
    return x + y;
}
```

Но этот код невалиден: бессмысленно складывать, например, два самолёта. И компилятор даже не знает, как складывать два самолёта! Здесь в игру вступают ограничения (constraints).

```rust
use std::ops::Add;


fn add<T: Add>(x: T, y: T) -> T {
    return x + y;
}
```

Здесь `add` может складывать любые типы, реализующие трейт `Add`. Кстати, именно так в Rust делается перегрузка операторов: путём реализации трейтов из модуля `std::ops`.

## 4.1 Дженерики

Цель обобщённого (generic) программирования — повысить переиспользуемость кода и снизить количество багов, позволяя функциям, структурам и трейтам определять свои типы позже.

На практике это означает, что алгоритм можно использовать с несколькими разными типами при условии, что они удовлетворяют ограничениям. В результате, если вы найдёте баг в вашем обобщённом алгоритме, вам нужно исправить его только один раз. Если бы вам пришлось реализовывать алгоритм 4 раза для 4 разных, но похожих типов (скажем, `int32`, `int64`, `float32`, `float64`), вы бы не просто потратили в 4 раза больше времени на реализацию, но и потратили бы в 4 раза больше времени на исправление одного и того же бага во всех реализациях (при условии, что вы не внесли другие баги из-за усталости).

В Rust функции, трейты (подробнее ниже) и типы данных могут быть обобщёнными:

```rust
use std::fmt::Display;


// a generic function, whose type parameter T is constrained
fn generic_display<T: Display>(item: T) {
    println!("{}", item);
}


// a generic struct
struct Point<T> {
    x: T,
    y: T,
}

// another generic struct
struct Point2<T>(T, T)


// a generic enum
enum Option<T> {
    Some(T),
    None
}


fn main() {
    let a: &str = "42";
    let b: i64 = 42;


    generic_display(a);
    generic_display(b);


    let (x, y) = (4i64, 2i64);


    let point: Point<i64> = Point {
         x,
         y
    };


    // generic_display(point) <- not possible. Point does not implement Display
}
```

Именно дженерики делают Rust таким выразительным. Без них было бы невозможно иметь обобщённые коллекции, такие как `Vec`, `HashMap` или `BTreeSet`.

```rust
use std::collections::HashMap;


struct Contact {
    name: String,
    email: String,
}


fn main() {
    // imagine a list of imported contacts with duplicates
    let imported_contacts = vec![
         Contact {
              name: "John".to_string(),
              email: "john@smith.com".to_string(),
         },
         Contact {
              name: "steve".to_string(),
              email: "steve@jobs.com".to_string(),
         },
         Contact {
              name: "John".to_string(),
              email: "john@smith.com".to_string(),
         },
         // ...
    ];


    let unique_contacts: HashMap<String, Contact> = imported_contacts
              .into_iter()
              .map(|contact| (contact.email.clone(), contact))
              .collect();
}
```

Благодаря мощи дженериков мы можем переиспользовать `HashMap` из стандартной библиотеки и быстро дедуплицировать наши данные!

Представьте, что вам пришлось бы реализовывать эти коллекции для каждого типа в ваших программах?

## 4.2 Трейты

Трейты — это эквивалент интерфейсов из других языков (с некоторыми отличиями).

Так как определение термина через его синоним не очень полезно, посмотрим, что это означает в коде:

```rust
pub trait Dog {
    fn bark(&self) -> String;
}


pub struct Labrador{}


impl Dog for Labrador {
    fn bark(&self) -> String {
         "wouf".to_string()
    }
}


pub struct Husky{}

impl Dog for Husky {
    fn bark(&self) -> String {
         "Wuuuuuu".to_string()
    }
}


fn main() {
    let labrador = Labrador{};
    println!("{}", labrador.bark());


    let husky = Husky{};
    println!("{}", husky.bark());
}


// Output:


// wouf
// Wuuuuuu
```

Определив интерфейс `Dog`, все типы, реализующие этот трейт в нашей программе, будут считаться «собакой».

Именно поэтому говорят, что трейты (и интерфейсы) позволяют программистам определять разделяемое поведение: поведение, которое разделяется несколькими типами.

### 4.2.1 Реализации по умолчанию

Можно предоставлять реализацию по умолчанию для методов трейта:

```rust
pub trait Hello {
    fn hello(&self) -> String {
          String::from("World")
    }
}


pub struct Sylvain {}


impl Hello for Sylvain {
    fn hello(&self) -> String {
          String::from("Sylvain")
    }
}


pub struct Anonymous {}


impl Hello for Anonymous {}


fn main() {
    let sylvain = Sylvain{};
    let anonymous = Anonymous{};


    println!("Sylvain: {}", sylvain.hello());
    println!("Anonymous: {}", anonymous.hello());
}
// Output:


// Sylvain: Sylvain
// Anonymous: World
```

### 4.2.2 Композиция трейтов

Трейты можно компоновать для более продвинутых ограничений:

```rust
pub trait Module {
     fn name(&self) -> String;
     fn description(&self) -> String;
}


pub trait SubdomainModule {
     fn enumerate(&self, domain: &str) -> Result<Vec<String>, Error>;
}


fn enumerate_subdomains<M: Module + SubdomainModule>(module: M, target: &str) ->
    Vec<String> {
     // ...
}
```

### 4.2.3 Асинхронные трейты

На сегодняшний день async-функции в трейтах не поддерживаются напрямую в Rust. К счастью, Дэвид Толней (David Tolnay) снова нас выручил: можно использовать крейт async-trait.

```rust
#[async_trait]
pub trait HttpModule: Module {
     async fn scan(
         &self,
         http_client: &Client,
         endpoint: &str,
     ) -> Result<Option<HttpFinding>, Error>;
}
```

### 4.2.4 Обобщённые трейты

Трейты также могут иметь обобщённые параметры:

```rust
use std::fmt::Display;


trait Printer<S: Display> {
     fn print(&self, to_print: S) {
         println!("{}", to_print);
     }


}


struct ActualPrinter{}


impl<S: Display, T> Printer<S> for T {}


fn main() {
    let s = "Hello";
    let n: i64 = 42;
    let printer = ActualPrinter{};


    printer.print(s);
    printer.print(n);
}


// output:


// Hello
// 42
```

И даже лучше: вы можете реализовать обобщённый трейт для обобщённого типа:

```rust
use std::fmt::Display;


trait Printer<S: Display> {
    fn print(&self, to_print: S) {
           println!("{}", to_print);
    }
}


// implements Printer<S: Display> for any type T
impl<S: Display, T> Printer<S> for T {}


fn main() {
    let s = "Hello";
    let printer: i64 = 42;


    printer.print(s);
}

// Output:


// Hello
```

### 4.2.5 Атрибут derive

Когда вам нужно реализовать много трейтов для ваших типов, это может быстро стать утомительным и усложнить ваш код.

К счастью, в Rust есть кое-что для нас: атрибут `derive`.

Используя атрибут derive, мы фактически передаём наши типы макросу Derive, который является своего рода процедурным макросом.

Они принимают код как вход (в данном случае наш тип) и создают больше кода как выход. На этапе компиляции.

Это особенно полезно для десериализации данных: просто реализовав трейты `Serialize` и `Deserialize` из крейта serde — почти повсеместно используемой библиотеки сериализации в мире Rust — мы можем сериализовать и десериализовать наши типы в множество форматов данных: JSON, YAML, TOML, BSON и так далее…

```rust
use serde::{Serialize, Deserialize};


#[derive(Debug, Clone, Serialize, Deserialize)]
struct Point {
    x: u64,
    y: u64,
}
```

Без особых усилий мы только что реализовали трейты `Debug`, `Clone`, `Serialize` и `Deserialize` для нашей структуры `Point`.

Стоит отметить, что все подполя вашей структуры должны реализовывать трейты:

```rust
use serde::{Serialize, Deserialize};


// Not possible:
#[derive(Debug, Clone, Serialize, Deserialize)]
struct Point<T> {
    x: T,
    y: T,
}


// instead, do this:
use serde::{Serialize, Deserialize};
use core::fmt::Debug; // Import the Debug trait


#[derive(Debug, Clone, Serialize, Deserialize)]
struct Point<T: Debug + Clone + Serialize + Deserialize> {
    x: T,
    y: T,
}
```

## 4.3 Трейтовые объекты (trait objects)

Теперь вы можете задаться вопросом: как создать коллекцию, которая может содержать разные конкретные типы, удовлетворяющие данному трейту? Например:

```rust
trait UsbModule {
     // ...
}


struct UsbCamera {
      // ...
}


impl UsbModule for UsbCamera {
     // ..
}


impl UsbCamera {
     // ...
}


struct UsbMicrophone{
      // ...
}

impl UsbModule for UsbMicrophone {
     // ..
}


impl UsbMicrophone {
     // ...
}


let peripheral_devices: Vec<UsbModule> = vec![
     UsbCamera::new(),
     UsbMicrophone::new(),
];
```

К сожалению, в Rust это не так просто. Так как модули могут иметь разный размер в памяти, компилятор не позволяет нам создать такую коллекцию. Не все элементы вектора имеют одинаковую форму.

Трейтовые объекты решают ровно эту проблему: когда вы хотите использовать разные конкретные типы (разной формы), придерживающиеся контракта (трейта), во время выполнения.

Вместо использования объектов напрямую мы будем использовать указатели на объекты в нашей коллекции. На этот раз компилятор примет наш код, потому что каждый указатель имеет одинаковый размер.

Как использовать это на практике? Мы увидим ниже при добавлении модулей в наш сканер.

### 4.3.1 Статическая и динамическая диспетчеризация

Итак, в чём техническая разница между обобщённым параметром и трейтовым объектом?

Когда вы используете обобщённый параметр (здесь для функции `process`): **ch_04/snippets/dispatch/src/statik.rs**

```rust
trait Processor {
    fn compute(&self, x: i64, y: i64) -> i64;
}


struct Risc {}


impl Processor for Risc {
    fn compute(&self, x: i64, y: i64) -> i64 {
         x + y
    }
}


struct Cisc {}


impl Processor for Cisc {
    fn compute(&self, x: i64, y: i64) -> i64 {
         x * y
    }
}


fn process<P: Processor>(processor: &P, x: i64) {
    let result = processor.compute(x, 42);
    println!("{}", result);
}


pub fn main() {
    let processor1 = Cisc {};
    let processor2 = Risc {};


    process(&processor1, 1);
    process(&processor2, 2);
}
```

Компилятор генерирует специализированную версию для каждого типа, с которым вы вызываете функцию, а затем заменяет места вызовов вызовами этих специализированных функций.

Это известно как мономорфизация.

Например, код выше примерно эквивалентен:

```rust
fn process_Risc(processor: &Risc, x: i64) {
    let result = processor.compute(x, 42);
    println!("{}", result);
}


fn process_Cisc(processor: &Cisc, x: i64) {
    let result = processor.compute(x, 42);
    println!("{}", result);
}
```

Это то же самое, как если бы вы реализовали эти функции сами. Это известно как статическая диспетчеризация. Выбор типа осуществляется статически на этапе компиляции. Он даёт лучшую производительность во время выполнения.

С другой стороны, когда вы используете трейтовый объект: **ch_04/snippets/dispatch/src/dynamic.rs**

```rust
trait Processor {
    fn compute(&self, x: i64, y: i64) -> i64;
}


struct Risc {}


impl Processor for Risc {
    fn compute(&self, x: i64, y: i64) -> i64 {
         x + y
    }
}


struct Cisc {}

impl Processor for Cisc {
    fn compute(&self, x: i64, y: i64) -> i64 {
         x * y
    }
}


fn process(processor: &dyn Processor, x: i64) {
    let result = processor.compute(x, 42);
    println!("{}", result);
}


pub fn main() {
    let processors: Vec<Box<dyn Processor>> = vec![
         Box::new(Cisc {}),
         Box::new(Risc {}),
    ];


    for processor in processors {
         process(&*processor, 1);
    }
}
```

Компилятор сгенерирует только 1 функцию `process`. Именно во время выполнения ваша программа обнаружит, к какому виду `Processor` относится переменная `processor` и, следовательно, какой метод `compute` вызывать. Это называется динамической диспетчеризацией. Выбор типа осуществляется динамически во время выполнения.

Синтаксис трейтовых объектов `&dyn Processor` может показаться немного тяжеловесным, особенно если вы пришли из менее многословных языков. Лично я его обожаю! С первого взгляда мы видим, что функция принимает трейтовый объект, благодаря `dyn Processor`.

Ссылка `&` обязательна, потому что Rust нужно знать точный размер каждой переменной.

Так как структуры, реализующие трейт `Processor`, могут различаться по размеру, единственное решение — передать ссылку. Это также мог бы быть умный указатель, такой как `Box`, `Rc` или `Arc`.

Суть в том, что переменная `processor` должна иметь размер, известный на этапе компиляции.

Заметьте: в этом конкретном примере мы делаем `&*processor`, потому что нам сначала нужно разыменовать `Box`, чтобы передать ссылку функции `process`. Это эквивалент `process(&(*processor), 1)`.

При компиляции функций с динамической диспетчеризацией Rust под капотом создаёт так называемую vtable и использует её во время выполнения, чтобы выбрать, какую функцию вызвать.

### 4.3.2 Несколько заключительных мыслей

Используйте статическую диспетчеризацию, когда вам нужна абсолютная производительность, и трейтовые объекты, когда вам нужно больше гибкости или коллекции объектов с одинаковым поведением.

## 4.4 Разбор аргументов командной строки

В первой главе мы видели, как получить доступ к аргументам командной строки. Для более сложных программ, таких как наш сканер, требуется библиотека для разбора аргументов командной строки.

Например, мы можем захотеть передать нашей программе более сложные параметры конфигурации, такие как формат вывода (JSON, XML…), флаг отладки или просто возможность выполнять несколько команд.

Мы будем использовать самую известную: clap, так как это также моя любимая. Но имейте в виду, что существуют альтернативы, например structopt.

```rust
    let cli = App::new(clap::crate_name!())
         .version(clap::crate_version!())
         .about(clap::crate_description!())
         .subcommand(SubCommand::with_name("modules").about("List all modules"))
         .subcommand(
             SubCommand::with_name("scan").about("Scan a target").arg(
                  Arg::with_name("target")
                       .help("The domain name to scan")
                       .required(true)
                       .index(1),
             ),
         )
         .setting(clap::AppSettings::ArgRequiredElseHelp)
         .setting(clap::AppSettings::VersionlessSubcommands)
         .get_matches();
```

Здесь мы объявляем 2 подкоманды: `modules` и `scan`.

Подкоманда `scan` также имеет обязательный аргумент: `target`. Таким образом, вызов `scan` так:

```text
$ tricoder scan
```

не сработает. Нужно вызывать её с аргументом:

```text
$ tricoder scan kerkour.com
```

Затем мы можем проверить, какая подкоманда была вызвана, и значение аргументов:

```rust
    if let Some(_) = cli.subcommand_matches("modules") {
         cli::modules();
    } else if let Some(matches) = cli.subcommand_matches("scan") {
         // we can safely unwrap as the argument is required
         let target = matches.value_of("target").unwrap();
         cli::scan(target)?;
     }
```

## 4.5 Логирование

Когда долго работающая программа сталкивается с нефатальной ошибкой, мы не всегда хотим прекращать её выполнение. Вместо этого хорошей практикой является запись ошибки в лог для дальнейшего расследования и отладки.

В Rust есть два замечательных крейта для логирования:

- log: для простого, текстового логирования
- slog: для более продвинутого структурированного логирования

Эти крейты, строго говоря, не являются логгерами. Вы можете добавить их в свои программы следующим образом:

**ch_04/snippets/logging/src/main.rs**

```rust
fn main() {
     log::info!("message with info level");
     log::error!("message with error level");
     log::debug!("message with debug level");
}
```

Но когда вы запускаете программу:

```text
$ cargo run
    Compiling logging v0.1.0 (black-hat-rust/ch_04/snippets/logging)
     Finished dev [unoptimized + debuginfo] target(s) in 0.56s
      Running `target/debug/logging`
```

Ничего не выводится…

Чтобы что-то действительно отображалось, нужен логгер. Крейты log и slog — лишь фасады.

Они предоставляют единый интерфейс логирования для всей экосистемы, но сами ничего не пишут в лог. Для этого нужен крейт-логгер.

### 4.5.1 env_logger

Список логгеров можно найти в документации крейта log: https://github.com/rust-lang/log#in-executables

На протяжении остальной части книги мы будем использовать env_logger, потому что он предоставляет большую гибкость и точность в том, что мы логируем, и, что более важно, прост в использовании.

Чтобы настроить его, просто экспортируйте переменную окружения `RUST_LOG` и вызовите функцию init следующим образом:

**ch_04/tricoder/src/main.rs**

```rust
env::set_var("RUST_LOG", "info,trust_dns_proto=error");
env_logger::init();
```

Здесь мы говорим env_logger логировать на уровне info по умолчанию и на уровне error для крейта trust_dns_proto.

- Модули для перечисления поддоменов
- Модули для сканирования каждого порта и поиска уязвимостей

Эти 2 вида модулей, при всей их разности, всё же могут иметь общие особенности.

Итак, объявим родительский трейт Module:

```rust
pub trait Module {
     fn name(&self) -> String;
     fn description(&self) -> String;
}
```

### 4.6.2 HTTP-модули

Цель HTTP-модуля: для данной конечной точки (`host:port`) проверить, можно ли найти данную уязвимость.

```rust
pub trait HttpModule: Module {
```

#### 4.6.2.2 Раскрытие git-файлов

Ещё один фатальный изъян — раскрытие git-файлов и каталогов.

Это часто случается с PHP-приложениями, обслуживаемыми nginx или Apache HTTP Server, когда они настроены неправильно.

Уязвимость заключается в том, чтобы оставить git-файлы публично доступными, например `.git/config` или `.git/HEAD`. (В большинстве случаев) можно скачать всю историю git с помощью скрипта.

Однажды я аудировал сайт компании, где мой друг был стажёром. Блог (WordPress, если я правильно помню) был восприимчив к этой уязвимости, и я смог скачать всю историю git проекта. Это было забавно, потому что у меня был доступ ко всем коммитам, которые мой друг сделал во время своей стажировки.

Но, что серьёзнее, учётные данные базы данных были закоммичены в код…

**ch_04/tricoder/src/modules/http/git_head_disclosure.rs**

```rust
impl GitHeadDisclosure {
    pub fn new() -> Self {
          GitHeadDisclosure {}
    }


    fn is_head_file(&self, content: &str) -> bool {
          return Some(0) == content.to_lowercase().trim().find("ref:");
    }
}

#[async_trait]
impl HttpModule for GitHeadDisclosure {
    async fn scan(
          &self,
          http_client: &Client,
          endpoint: &str,
    ) -> Result<Option<HttpFinding>, Error> {
          let url = format!("{}/.git/HEAD", &endpoint);
          let res = http_client.get(&url).send().await?;


          if !res.status().is_success() {
                return Ok(None);
          }


          let body = res.text().await?;
          if self.is_head_file(&body) {
                return Ok(Some(HttpFinding::GitHeadDisclosure(url)));
          }


          Ok(None)
    }
}
```

#### 4.6.2.3 Раскрытие файла .env

Раскрытие файла `.env` — тоже из тех уязвимостей, которые легко упустить, но которые могут быть фатальны: они могут вскрыть все секреты вашего веб-приложения, такие как учётные данные базы данных или SMTP, ключи шифрования…

**ch_04/tricoder/src/modules/http/dotenv_disclosure.rs**

```rust
#[async_trait]
impl HttpModule for DotEnvDisclosure {
    async fn scan(
          &self,
          http_client: &Client,
          endpoint: &str,
    ) -> Result<Option<HttpFinding>, Error> {
          let url = format!("{}/.env", &endpoint);
          let res = http_client.get(&url).send().await?;


          if res.status().is_success() {
                return Ok(Some(HttpFinding::DotEnvFileDisclosure(url)));
          }


          Ok(None)
    }
}
```

Обратите внимание: этот модуль не так надёжен, и вам, возможно, стоит добавить сопоставление с регулярным выражением, чтобы убедиться, что приложение не возвращает валидный ответ для любого URL. Например, `[A-Z0-9]+=.*`.

#### 4.6.2.4 Раскрытие файла .DS_Store

Раскрытие файла `.DS_Store` более тонкое. Оно менее катастрофично, чем, например, раскрытие файла `.env`.

Попав наружу, файл `.DS_Store` может раскрыть другие чувствительные файлы, забытые в папке, такие как `database_backup.sql`, или всю структуру приложения.

**ch_04/tricoder/src/modules/http/ds_store_disclosure.rs**

```rust
impl DsStoreDisclosure {
    pub fn new() -> Self {
          DsStoreDisclosure {}
    }


    fn is_ds_store_file(&self, content: &[u8]) -> bool {
          if content.len() < 8 {
                return false;
          }


          let signature = [0x0, 0x0, 0x0, 0x1, 0x42, 0x75, 0x64, 0x31];


          return content[0..8] == signature;
    }
}


#[async_trait]
impl HttpModule for DsStoreDisclosure {
    async fn scan(
          &self,
          http_client: &Client,
          endpoint: &str,
    ) -> Result<Option<HttpFinding>, Error> {
          let url = format!("{}/.DS_Store", &endpoint);
          let res = http_client.get(&url).send().await?;

          if !res.status().is_success() {
                return Ok(None);
          }


          let body = res.bytes().await?;
          if self.is_ds_store_file(&body.as_ref()) {
                return Ok(Some(HttpFinding::DsStoreFileDisclosure(url)));
          }


          Ok(None)
    }
}
```

#### 4.6.2.5 Неаутентифицированный доступ к базам данных

В последние годы не было ни одного месяца, чтобы какая-то компания не была взломана или не была выкуплена из-за того, что оставила базу данных без аутентификации в интернете. Худшими нарушителями являются MongoDB и Elasticsearch. Менее известный (более нишевый, нацеленный на облачную инфраструктуру), но всё же важный — etcd.

Для etcd это можно обнаружить сопоставлением строк: **ch_04/tricoder/src/modules/http/etcd_unauthenticated_access.rs**

```rust
#[async_trait]
impl HttpModule for EtcdUnauthenticatedAccess {
    async fn scan(
          &self,
          http_client: &Client,
          endpoint: &str,
    ) -> Result<Option<HttpFinding>, Error> {
          let url = format!("{}/version", &endpoint);
          let res = http_client.get(&url).send().await?;


          if !res.status().is_success() {
                return Ok(None);
          }


          let body = res.text().await?;
          if body.contains(r#""etcdserver""#)
                && body.contains(r#""etcdcluster""#)
                && body.chars().count() < 200
          {
                return Ok(Some(HttpFinding::EtcdUnauthenticatedAccess(url)));
          }


          Ok(None)
    }
}
```

#### 4.6.2.6 Неаутентифицированный доступ к админ-дашбордам

Ещё один конфигурационный просчёт, который может быть фатальным, — оставить дашборды открытыми миру.

По моему опыту, главные нарушители: kibana, traefik, zabbix и Prometheus.

Сопоставления строк в большинстве случаев достаточно: **ch_04/tricoder/src/modules/http/kibana_unauthenticated_access.rs**

```rust
#[async_trait]
impl HttpModule for KibanaUnauthenticatedAccess {
    async fn scan(
          &self,
          http_client: &Client,
          endpoint: &str,
    ) -> Result<Option<HttpFinding>, Error> {
          let url = format!("{}", &endpoint);
          let res = http_client.get(&url).send().await?;


          if !res.status().is_success() {
                return Ok(None);
          }

          let body = res.text().await?;
          if body.contains(r#"</head><body kbn-chrome
              id="kibana-body"><kbn-initial-state"#)
          || body.contains(r#"<div
              class="ui-app-loading"><h1><strong>Kibana</strong><small>&nbsp;is
              loading."#)
          || Some(0) == body.find(r#"|| body.contains("#)
          || body.contains(r#"<div class="kibanaWelcomeLogo"></div></div></div><div
              class="kibanaWelcomeText">Loading Kibana</div></div>"#) {
                return Ok(Some(HttpFinding::KibanaUnauthenticatedAccess(
                       url,
                )));
          }


          Ok(None)
    }
}
```

#### 4.6.2.7 Раскрытие листинга каталогов

Также распространённая ошибка в PHP-приложениях, обслуживаемых Nginx и Apache server: эта ошибка конфигурации позволяет всему миру просматривать файлы в папках сервера. Просто безумие, сколько личных и корпоративных данных можно получить с помощью google dorks, таких как:

```text
intitle:"index.of" "parent directory" "size"
```

**ch_04/tricoder/src/modules/http/directory_listing_disclosure.rs**

```rust
// ...
impl DirectoryListingDisclosure {
    pub fn new() -> Self {
         DirectoryListingDisclosure {
             dir_listing_regex: Regex::new(r"<title>Index of .*</title>")
                    .expect("compiling http/directory_listing regexp"),
         }
    }


    async fn is_directory_listing(&self, body: String) -> Result<bool, Error> {
         let dir_listing_regex = self.dir_listing_regex.clone();
         let res = tokio::task::spawn_blocking(move ||
           dir_listing_regex.is_match(&body)).await?;


         Ok(res)
    }
}


// ...


#[async_trait]
impl HttpModule for DirectoryListingDisclosure {
    async fn scan(
         &self,
         http_client: &Client,
         endpoint: &str,
    ) -> Result<Option<HttpFinding>, Error> {
         let url = format!("{}/", &endpoint);
         let res = http_client.get(&url).send().await?;


         if !res.status().is_success() {
             return Ok(None);
         }


         let body = res.text().await?;
         if self.is_directory_listing(body).await? {
             return Ok(Some(HttpFinding::DirectoryListingDisclosure(url)));
         }


         Ok(None)
    }
}
```

## 4.7 Тесты

Теперь, когда у нас есть модули, как мы можем быть уверены, что не допустили ошибок при написании кода?

Тесты, конечно!

Главная ошибка, которой следует избегать при написании тестов, — писать тесты, отталкиваясь от тестируемой реализации.

Так делать не стоит!

Тесты должны писаться исходя из спецификации. Например, при тестировании раскрытия файла `.DS_Store` у нас могут быть неправильные магические байты в нашем коде. Поэтому мы должны писать тест, глядя на спецификацию файла `.DS_Store`, а не на нашу собственную реализацию.

**ch_04/tricoder/src/modules/http/ds_store_disclosure.rs**

```rust
#[cfg(test)]
mod tests {
    #[test]
    fn is_ds_store() {
         let module = super::DsStoreDisclosure::new();
         let body = "testtesttest";
         let body2 = [
               0x00, 0x00, 0x00, 0x01, 0x42, 0x75, 0x64, 0x31, 0x00, 0x00, 0x30, 0x00,
                  0x00, 0x00,
               0x08, 0x0,
         ];


         assert_eq!(false, module.is_ds_store_file(body.as_bytes()));
         assert_eq!(true, module.is_ds_store_file(&body2));
    }
}
```

### 4.7.1 Асинхронные тесты

Благодаря tokio написание асинхронных тестов — всего лишь пара нажатий клавиш.

**ch_04/tricoder/src/modules/http/directory_listing_disclosure.rs**

```rust
#[cfg(test)]
mod tests {
    use super::DirectoryListingDisclosure;


    #[tokio::test]
    async fn is_directory_listing() {
        let module = DirectoryListingDisclosure::new();


        let body = String::from("Content <title>Index of kerkour.com</title> test");
        let body2 = String::from(">ccece> Contrnt <tle>Index of kerkour.com</title>
            test");
        let body3 = String::from("");
        let body4 = String::from("test test test test test< test> test
            <title>Index</title> test");


        assert_eq!(true, module.is_directory_listing(body).await.unwrap());
        assert_eq!(false, module.is_directory_listing(body2).await.unwrap());
        assert_eq!(false, module.is_directory_listing(body3).await.unwrap());
        assert_eq!(false, module.is_directory_listing(body4).await.unwrap());
    }
}
```

### 4.7.2 Автоматизация тестов

**Рисунок 4.2: CI-конвейер**

![Рисунок 4.2](figures/figure-4.2.png)


Тесты не предназначены для ручного запуска при каждом написании кода. Это было бы неразумным использованием вашего драгоценного времени. Действительно, Rust (по своей конструкции) компилируется очень-очень долго. Запуск тестов на своей машине более нескольких раз в день нарушил бы вашу концентрацию.

Вместо этого тесты следует запускать из CI (Continuous Integration — непрерывной интеграции). CI-системы — это конвейеры, которые вы настраиваете; они будут запускать ваши тесты при каждой отправке кода. В наши дни практически все платформы кода (GitHub, GitLab, sourcehut…) предоставляют встроенный CI. Примеры CI-рабочих процессов для Rust-проектов можно найти здесь: https://github.com/skerkour/phaser/tree/main/.github/workflows

```yaml
name: CI

# This workflow run tests and build for each push


on:
  push:
      branches:
        - main
        - 'feature-**'


jobs:


  test_phaser:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v2


        - name: Update local toolchain
          run: |
            rustup update
            rustup component add clippy
            rustup install nightly


        - name: Toolchain info
          run: |
            cargo --version --verbose
            rustc --version
            cargo clippy --version


        - name: Lint
          run: |
            cd phaser
            cargo fmt -- --check
            cargo clippy -- -D warnings


        - name: Test
          run: |
            cd phaser
            cargo check
            cargo test --all


        - name: Build
          run: |
            cd phaser
            cargo build --release
```

## 4.9 Краткое содержание

- Используйте обобщённые параметры, когда хотите абсолютной производительности, и трейтовые объекты, когда хотите больше гибкости.
- Прежде чем искать продвинутые уязвимости, ищите ошибки конфигурации.
- Понимание того, как устроена система, упрощает процесс выявления уязвимостей конфигурации.
- Никогда не пишите тесты, глядя на тестируемый код. Вместо этого смотрите на спецификацию.
- Используйте CI для запуска тестов вместо локального запуска.
