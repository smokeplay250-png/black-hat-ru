# Глава 5. Обход веба для OSINT

## 5.1 OSINT

OSINT расшифровывается как Open Source Intelligence (разведка по открытым источникам). Чтобы было ясно, часть «Open Source» не имеет ничего общего с тем Open Source, который вы привыкли видеть.

OSINT можно определить как методы и инструменты, использующие публично доступную информацию для поддержки разведывательного анализа (расследования, разведки).

Так как OSINT состоит в извлечении значащей информации из большого объёма данных, его можно и нужно автоматизировать.

## 5.2 Инструменты

## 5.3 Поисковые системы

Назначение поисковой системы — превратить океан данных в искомую и пригодную для действий информацию.

Поисковая система состоит из следующих частей:

- Краулеры (обходчики), которые плавают по океану данных и превращают его в структурированные данные
- Индекс, используемый для хранения структурированных данных, извлечённых краулерами
- И интерфейс поиска, используемый для запросов к индексу

**Рисунок 5.1: Части поисковой системы**

![Рисунок 5.1](figures/figure-5.1.png)


Почему это важно?

Потому что по своей сути OSINT — это построение специализированной поисковой системы о наших целях: вы обходите данные из других баз данных и индексируете только значащую информацию о вашей цели для последующего поиска. Будь то в markdown-отчёте, в maltego или в традиционной базе данных, такой как PostgreSQL.

Как мы увидим, поисковые системы не ограничиваются вебом (как Google или Bing). Существуют также поисковые системы по серверам и IoT (интернету вещей).

К сожалению для нас, большинство публичных поисковых систем вежливы: они уважают файлы robots.txt и потому могут пропускать интересные данные. Более того, они не обходят страницы, скрытые за экраном входа в систему.

Вот почему нам также нужно уметь строить собственные краулеры.

Вот несколько примеров google dorks для поиска сочных целей:

## 5.9 Обход веба

Во-первых, уточнение терминов: в чём разница между скрейпером (scraper) и краулером (crawler)?

Скрейпинг — это процесс превращения неструктурированных веб-данных в структурированные.

**Рисунок 5.3: Веб-скрейпинг**

![Рисунок 5.3](figures/figure-5.3.png)


Краулинг — это процесс прохода через множество взаимосвязанных данных (например, веб-страниц).

На практике в большинстве случаев бесполезно скрейпить без обхода нескольких страниц или обходить страницы без скрейпинга контента, поэтому можно сказать, что каждый краулер — это скрейпер, и почти каждый скрейпер — это краулер.

Некоторые люди предпочитают называть скрейпером краулер для конкретного сайта, а краулером — то, что обходит весь веб. Как бы то ни было, я думаю, это придирки, и мы не будем тратить время на споры.

На протяжении остальной части книги мы будем использовать термин «краулер».

Итак, зачем обходить веб-сайты, чтобы скрейпить данные?

Всё дело в автоматизации. Да, вы можете вручную просматривать тысячи страниц сайта и вручную копировать/вставлять данные в электронную таблицу.

Или вы можете построить специализированную программу — краулер, который сделает это за вас в мгновение ока.

### 5.9.1 Проектирование краулера

Краулер состоит из следующих частей:

**Рисунок 5.4: Архитектура краулера**

![Рисунок 5.4](figures/figure-5.4.png)


Стартовые URL: вам нужен список стартовых URL, с которых начать обход. Например, корневая страница сайта вашей цели.

Пауки (Spiders): это специализированная часть краулера, настроенная под конкретный сайт или задачу. Например, мы могли бы реализовать паука для получения всех пользователей GitHub-организации или всех уязвимостей конкретного продукта. Паук сам состоит из 2 частей:

- Скрейпер, который получает URL, разбирает данные, превращает их в структурированные данные и в список URL, извлечённых из документа, для продолжения обхода.
- Процессор, который обрабатывает структурированные данные: например, сохраняет их в базу данных.

Самое большое преимущество разделения обязанностей паука на 2 отдельные стадии в том, что их можно запускать с разной степенью конкурентности в зависимости от ожидаемой рабочей нагрузки. Например, у вас может быть пул из 3 конкурентных скрейперов, чтобы не залить сайт, который вы обходите, и не триггернуть системы обнаружения ботов, на 100 конкурентных процессорах.

Цикл управления (Control loop): это общая часть краулера. Его работа — распределять данные между скрейперами и процессорами и ставить URL в очередь.

## 5.10 Почему Rust для краулинга

Теперь вы можете задаться вопросом: почему Rust для краулинга? В конце концов, у Python и Go уже есть солидная экосистема вокруг этой задачи (соответственно Scrapy и Colly).

### 5.10.1 Async

Первая и, возможно, самая важная причина использования Rust — его асинхронная модель ввода/вывода: вы гарантированно получаете лучшую возможную производительность при выполнении сетевых запросов.

### 5.10.2 Производительность, связанная с памятью

Выполнение множества сетевых запросов и разбор данных часто требует создания множества недолговечных объектов памяти, что создаёт большое давление на сборщики мусора. Так как у Rust нет сборщика мусора, у него нет этой проблемы, и использование памяти будет гораздо более детерминированным.

### 5.10.3 Безопасность при разборе

Скрейпинг требует разбора (parsing). Разбор — один из самых распространённых способов внести уязвимости (Parsing JSON is a Minefield, уязвимости разбора XML) или баги. Rust, с другой стороны, благодаря безопасности памяти и строгой обработке ошибок предоставляет лучшие инструменты для решения сложной задачи разбора ненадёжных данных и сложных форматов.

## 5.11 Ассоциированные типы

Теперь мы в курсе, что такое краулер и почему именно Rust. Давайте изучим последние пару особенностей Rust, необходимых для построения краулера.

Последний важный момент о дженериках в Rust — ассоциированные типы.

Вы уже имели дело с ассоциированными типами при использовании итераторов и Futures.

Помните `Future<Output=String>`? Здесь `String` — ассоциированный тип.

Мы могли бы построить обобщённого паука так:

```rust
pub trait Spider<I>{
    fn name(&self) -> String;
    fn start_urls(&self) -> Vec<String>;
    async fn scrape(&self, url: &str) -> Result<(Vec<I>, Vec<String>), Error>;
    async fn process(&self, item: I) -> Result<(), Error>;
}
```

Но тогда его было бы очень неудобно использовать, так как каждая использующая его функция также должна быть обобщённой по `I`:

```rust
fn use_spider<I, S: Spider<I>>(spider: S) {
    // ...
}
```

Используя ассоциированный тип, мы упрощаем использование трейта и более ясно сообщаем, как он работает:

```rust
#[async_trait]
pub trait Spider {
    type Item;


    fn name(&self) -> String;
    fn start_urls(&self) -> Vec<String>;
    async fn scrape(&self, url: &str) -> Result<(Vec<Self::Item>, Vec<String>),
        Error>;
    async fn process(&self, item: Self::Item) -> Result<(), Error>;
}


fn use_spider<S: Spider>(spider: S) {
    // ...
}
```

Как и с параметрами типов, к ассоциированным типам можно добавлять ограничения:

```rust
pub trait Spider {
    type Item: Debug + Clone;


    fn name(&self) -> String;
    fn start_urls(&self) -> Vec<String>;
    async fn scrape(&self, url: &str) -> Result<(Vec<Self::Item>, Vec<String>),
        Error>;
    async fn process(&self, item: Self::Item) -> Result<(), Error>;
}
```

## 5.12 Атомарные типы

Атомарные типы, как и мьютексы, — типы разделяемой памяти: их можно безопасно разделять между несколькими потоками.

Они позволяют не использовать мьютекс, а вместе с ним и весь ритуал вокруг `lock()`, который может внести такие баги, как взаимоблокировки.

Следует использовать атомарный тип, если вы хотите разделять `bool` или целое число (например, счётчик) между потоками, вместо `Mutex<bool>` или `Mutex<i64>`.

Операции над атомарными типами требуют аргумент упорядочивания (ordering). Причина выходит за рамки этой книги, но подробнее об этом можно прочитать в этом превосходном посте: Explaining Atomics in Rust (возможно оно https://github.com/cfsamson).

Чтобы всё было просто, используйте `Ordering::SeqCst`, который даёт самые сильные гарантии.

**ch_05/snippets/atomic/src/main.rs**

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use std::thread;


fn main() {
    // creating a new atomic
    let my_atomic = AtomicUsize::new(42);


    // adding 1
    my_atomic.fetch_add(1, Ordering::SeqCst);


    // geting the value
    assert!(my_atomic.load(Ordering::SeqCst) == 43);


    // substracting 1
    my_atomic.fetch_sub(1, Ordering::SeqCst);


    // replacing the value
    my_atomic.store(10, Ordering::SeqCst);
    assert!(my_atomic.load(Ordering::SeqCst) == 10);


    // other avalable operations
    // fetch_xor, fetch_or, fetch_nand, fetch_and...


    // creating a new atomic that can be shared between threads
    let my_arc_atomic = Arc::new(AtomicUsize::new(4));

    let second_ref_atomic = my_arc_atomic.clone();
    thread::spawn(move|| {
          second_ref_atomic.store(42, Ordering::SeqCst);
    });
}
```

## 5.13 Барьер (Barrier)

Барьер — как `sync.WaitGroup` в Go: он позволяет нескольким конкурентным операциям синхронизироваться.

```rust
use tokio::sync::Barrier;
use std::sync::Arc;


#[tokio::main]
async fn main() {
     // number of concurrent operations
     let barrier = Arc::new(Barrier::new(3));


     let b2 = barrier.clone()
     tokio::spawn(async move {
           // do things
           b2.wait().await;
     });


     let b3 = barrier.clone()
     tokio::spawn(async move {
           // do things
           b3.wait().await;
     });

     barrier.wait().await;


     println!("This will print only when all the three concurrent operations have
           terminated");
}
```

## 5.16 Реализация краулера

**ch_05/crawler/src/crawler.rs**

```rust
     pub async fn run<T: Send + 'static>(&self, spider: Arc<dyn Spider<Item = T>>) {
          let mut visited_urls = HashSet::<String>::new();
          let crawling_concurrency = self.crawling_concurrency;
          let crawling_queue_capacity = crawling_concurrency * 400;
          let processing_concurrency = self.processing_concurrency;
          let processing_queue_capacity = processing_concurrency * 10;
          let active_spiders = Arc::new(AtomicUsize::new(0));


          let (urls_to_visit_tx, urls_to_visit_rx) =
              mpsc::channel(crawling_queue_capacity);
          let (items_tx, items_rx) = mpsc::channel(processing_queue_capacity);
          let (new_urls_tx, mut new_urls_rx) = mpsc::channel(crawling_queue_capacity);
          let barrier = Arc::new(Barrier::new(3));


          for url in spider.start_urls() {
               visited_urls.insert(url.clone());
               let _ = urls_to_visit_tx.send(url).await;
          }


          self.launch_processors(
             processing_concurrency,
             spider.clone(),
             items_rx,
             barrier.clone(),
        );


        self.launch_scrapers(
             crawling_concurrency,
             spider.clone(),
             urls_to_visit_rx,
             new_urls_tx.clone(),
             items_tx,
             active_spiders.clone(),
             self.delay,
             barrier.clone(),
        );
```

И, наконец, цикл управления, где мы ставим в очередь новые URL, которые ещё не были посещены, и проверяем, не пора ли остановить краулер.

Сбрасывая `urls_to_visit_tx`, мы закрываем каналы и, таким образом, останавливаем скрейперы, когда они все закончат обрабатывать оставшиеся URL в канале.

```rust
        loop {
             if let Some((visited_url, new_urls)) = new_urls_rx.try_recv().ok() {
                  visited_urls.insert(visited_url);

                  for url in new_urls {
                      if !visited_urls.contains(&url) {
                             visited_urls.insert(url.clone());
                             log::debug!("queueing: {}", url);
                             let _ = urls_to_visit_tx.send(url).await;
                      }
                  }
             }


             if new_urls_tx.capacity() == crawling_queue_capacity // new_urls channel
                 is empty
             && urls_to_visit_tx.capacity() == crawling_queue_capacity //
                 urls_to_visit channel is empty
             && active_spiders.load(Ordering::SeqCst) == 0
             {
                  // no more work, we leave
                  break;
             }

                sleep(Duration::from_millis(5)).await;
          }


          log::info!("crawler: control loop exited");


          // we drop the transmitter in order to close the stream
          drop(urls_to_visit_tx);


          // and then we wait for the streams to complete
          barrier.wait().await;
    }
```

Выполнять процессоры конкурентно — вопрос лишь создания новой задачи с потоком (stream) и `for_each_concurrent`. Как только поток останавливается, мы «уведомляем» барьер.

```rust
    fn launch_processors<T: Send + 'static>(
          &self,
          concurrency: usize,
          spider: Arc<dyn Spider<Item = T>>,
          items: mpsc::Receiver<T>,
          barrier: Arc<Barrier>,
    ) {
          tokio::spawn(async move {
                tokio_stream::wrappers::ReceiverStream::new(items)
                    .for_each_concurrent(concurrency, |item| async {
                         let _ = spider.process(item).await;
                    })
                    .await;


                barrier.wait().await;
          });
    }
```

Наконец, запуск скрейперов, как и процессоров, требует новой задачи с потоком и `for_each_concurrent`.

Логика здесь немного сложнее:

- сначала мы инкрементируем `active_spiders`
- затем скрейпим URL и извлекаем данные и следующие URL для посещения
- затем отправляем эти элементы процессорам
- также отправляем недавно найденные URL в цикл управления
- и спим в течение настроенной задержки, чтобы не залить сервер
- наконец, декрементируем `active_spiders`

Сбрасывая `items_tx`, мы закрываем канал элементов и, таким образом, останавливаем процессоры, когда канал опустеет.

```rust
    fn launch_scrapers<T: Send + 'static>(
          &self,
          concurrency: usize,
          spider: Arc<dyn Spider<Item = T>>,
          urls_to_vist: mpsc::Receiver<String>,
          new_urls: mpsc::Sender<(String, Vec<String>)>,
          items_tx: mpsc::Sender<T>,
          active_spiders: Arc<AtomicUsize>,
          delay: Duration,
          barrier: Arc<Barrier>,
    ) {
          tokio::spawn(async move {
              tokio_stream::wrappers::ReceiverStream::new(urls_to_vist)
                   .for_each_concurrent(concurrency, |queued_url| {
                        let queued_url = queued_url.clone();
                        async {
                             active_spiders.fetch_add(1, Ordering::SeqCst);
                             let mut urls = Vec::new();
                             let res = spider
                                  .scrape(queued_url.clone())
                                  .await
                                  .map_err(|err| {
                                       log::error!("{}", err);
                                       err
                                  })
                                  .ok();


                             if let Some((items, new_urls)) = res {
                                  for item in items {
                                       let _ = items_tx.send(item).await;
                                  }
                                  urls = new_urls;
                             }


                             let _ = new_urls.send((queued_url, urls)).await;
                             sleep(delay).await;
                             active_spiders.fetch_sub(1, Ordering::SeqCst);
                        }
                   })
                   .await;


               drop(items_tx);
               barrier.wait().await;
         });
    }
```

Так как наш краулер не будет делать тонну запросов, нам не нужно использовать токен для аутентификации в API Github, но нужно настроить некоторые заголовки. Иначе сервер заблокирует наши запросы.

Наконец, нам также нужно регулярное выражение — быстрый и грязный способ найти следующую страницу для обхода:

```rust
pub struct GitHubSpider {
    http_client: Client,
    page_regex: Regex,
    expected_number_of_results: usize,
}


impl GitHubSpider {
    pub fn new() -> Self {
        let http_timeout = Duration::from_secs(6);
        let mut headers = header::HeaderMap::new();
        headers.insert(
             "Accept",
             header::HeaderValue::from_static("application/vnd.github.v3+json"),
        );


        let http_client = Client::builder()
             .timeout(http_timeout)
             .default_headers(headers)
             .user_agent(
                 "Mozilla/5.0 (Windows NT 6.1; Win64; x64; rv:47.0) Gecko/20100101
                     Firefox/47.0",
             )
             .build()
             .expect("spiders/github: Building HTTP client");


        // will match https://...?page=XXX
        let page_regex =
             Regex::new(".*page=([0-9]*).*").expect("spiders/github: Compiling page
                 regex");


        GitHubSpider {
             http_client,
             page_regex,
             expected_number_of_results: 100,
        }
    }
}
```

Извлечение элемента — вопрос лишь разбора JSON, что легко благодаря reqwest, предоставляющему метод `json`.

Здесь трюк — найти следующий URL для посещения. Для этого мы используем скомпилированное выше регулярное выражение и захватываем номер текущей страницы. Например, в `...&page=2` мы захватываем `2`.

Затем мы разбираем эту String в число, инкрементируем это число и заменяем исходный URL новым числом. Таким образом, новый URL будет `...&page=3`.

Если API не возвращает ожидаемое количество результатов (которое настраивается параметром запроса `per_page`), это означает, что мы на последней странице результатов, и обходить больше нечего.

**ch_05/crawler/src/spiders/github.rs**

```rust
async fn scrape(&self, url: String) -> Result<(Vec<GitHubItem>, Vec<String>),
   Error> {
    let items: Vec<GitHubItem> =
        self.http_client.get(&url).send().await?.json().await?;


    let next_pages_links = if items.len() == self.expected_number_of_results {
           let captures = self.page_regex.captures(&url).unwrap();
           let old_page_number = captures.get(1).unwrap().as_str().to_string();
           let mut new_page_number = old_page_number
                .parse::<usize>()
                .map_err(|_| Error::Internal("spider/github: parsing page
                    number".to_string()))?;
           new_page_number += 1;


           let next_url = url.replace(
                format!("&page={}", old_page_number).as_str(),
                format!("&page={}", new_page_number).as_str(),
           );
           vec![next_url]
    } else {
        Vec::new()
    };


    Ok((items, next_pages_links))
}
```

## 5.20 Как защищаться

БОЛЬШАЯ проблема — определить, является ли посетитель легитимным или ботом. На эту конкретную проблему тратятся миллионы, и нынешние системы крупнейших корпораций всё ещё далеки от совершенства. Вот почему вам иногда приходится заполнять эти раздражающие капчи.

Давайте будем честны. Вы не можете защититься от решительного программиста, желающего скрейпить ваш сайт. Вы можете лишь внедрить меры, которые затруднят ему жизнь.

Вот несколько техник отлова краулеров.

### 5.20.1 Бесконечные редиректы, циклы и медленные страницы

Первый метод — простая ловушка: вы можете создать фиктивные страницы, на которые пользователи никогда не должны попадать, а плохой бот — попадёт. Эти фиктивные страницы вели бы бесконечно на другие фиктивные страницы, ведущие на другие фиктивные страницы.

Например, `/trap/1` вела бы на `/trap/2`, которая вела бы на `/trap/3`…

Вы также можете намеренно замедлить эти фиктивные страницы:

```javascript
function serve_page(req, res) {
    if (bot_is_detected()) {
         sleep(10 * time.Second)
         return res.send_dummy_page();
    }
}
```

Хороший трюк для поимки плохих ботов — добавить эти ловушки в секцию `disallow` вашего файла robots.txt.

### 5.20.2 Zip-бомбардировка

Второй метод — безусловно, самый наступательный.

Он состоит в злоупотреблении внутренними алгоритмами сжатия для создания файла `.zip` или `.gzip`, который мал (несколько килобайт/мегабайт), но после распаковки весит многие гигабайты, из-за чего краулер исчерпает всю свою память до краша.

Вот как просто создать такой файл:

```text
$ dd if=/dev/zero bs=1M count=10000 | gzip > 10G.gzip
$ du -sh 10G.gzip
$ 10M      10G.gzip
```

Затем, когда бот обнаружен, отдавайте этот файл вместо легитимной HTML-страницы:

```javascript
function serve_page(req, res) {
     if (bot_is_detected()) {
          res.set_header("Content-Encoding", "gzip")
          return res.send_file("10G.gzip");
     }
}
```

Почему GZip? Потому что GZip почти повсеместно автоматически обрабатывается HTTP-клиентами. Поэтому, просто запросив URL, краулер упадёт.

### 5.20.3 Плохие данные

Наконец, последний метод — защита от первопричины того, почему вас вообще скрейпят: от данных.

Идея проста: если вы достаточно уверены в своём алгоритме обнаружения ботов (я думаю, не стоит быть настолько уверенным), вы можете отдавать краулерам гнилые и отравленные данные.

Другой, более тонкий подход — отдавать «заражённые данные»: данные со встроенными маркерами, которые позволят вам идентифицировать скрейперов и припереть их к стенке, например, невозможную дату или вымышленные имена.
